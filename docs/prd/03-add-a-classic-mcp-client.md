# Add a classic MCP client

Status: **proposed**. Written as a proposal: it records what the client
speaks today, what a server that has not migrated expects, the parts of the
existing implementation that carry over unchanged, the parts that cannot, and
the order of the work so that every step leaves `make check` green and the
modern client untouched.

## 1. The problem

AgentKit's MCP client speaks revision `2026-07-28` and nothing else. That
revision removed the `initialize`/`notifications/initialized` handshake,
protocol-level sessions and `Mcp-Session-Id`, `ping`, the HTTP GET stream and
`Last-Event-ID` resumability, and server-initiated requests; version, identity
and capabilities travel in every request's `_meta`. A server that has not
migrated cannot be talked to at all. The README says so under *What is not
built*, `docs/PROVIDERS.md` says so twice (ruling L-1 and *The cost of
modern-only*), and the `mcp` example says so in its package comment.

The cost was accepted knowingly in PRD 0.4.0 and it is the cost the ruling
predicted: *"a server that has not migrated is unreachable, and at the time
of the ruling most have not."* That is still the state of the world. Every
published reference server, every vendor-hosted remote server and every
server generated by the official SDKs speaks the handshake era, at one of
three revisions:

| Revision | What it added over the one before | Transports |
|---|---|---|
| `2024-11-05` | The base: `initialize`, capabilities, `ping`, tools, resources, prompts, sampling, roots, logging, progress, cancellation. | stdio, HTTP+SSE (two endpoints) |
| `2025-03-26` | Streamable HTTP (one endpoint, `Mcp-Session-Id`, GET stream, resumability), JSON-RPC batching, tool annotations, audio content, completions, an authorization framework. | stdio, Streamable HTTP, HTTP+SSE kept for compatibility |
| `2025-06-18` | Batching **removed**, `structuredContent` and `outputSchema`, elicitation, resource links, `title` fields, `_meta` on every type, the `MCP-Protocol-Version` header on every post-handshake HTTP request. | stdio, Streamable HTTP; HTTP+SSE deprecated |

This document calls those three, collectively, the **classic** era, and
`2026-07-28` the **modern** one, which is the spec's own split: it calls an
implementation that speaks both *dual-era*.

Ruling L-1 says *"Reversal means implementing the legacy era, not a flag."*
This PRD is that implementation. It does not re-litigate the ruling; it pays
the price the ruling named, and asks for the ruling to be amended to record
that the price was paid.

## 2. Goals and non-goals

**Goals.**

1. An AgentKit embedder can consume tools from a classic server over stdio
   and Streamable HTTP, through the same `Pool`, the same qualified names,
   the same collision check, call limit, timeout, result cap, audit trail,
   reconnect budget and `BeforeToolCall` gate the modern client has. A
   `core.Tool` adapted from a classic server is indistinguishable from one
   adapted from a modern server, everywhere above `mcp`.
2. The modern client is not changed in behaviour, and an embedder that does
   not import the classic package pays nothing: no new code in the modern
   path, no new exported surface it has to understand, no change to the
   root's dependency graph (the root still requires nothing outside the
   standard library, and `internal/policy` still proves it).
3. Every REQ-SEC-11 and REQ-SEC-12 obligation holds on the new surface
   exactly as on the old: bounded before allocating, duplicate keys rejected,
   strict envelope, unknown protocol members rejected, poisoned on the first
   malformed frame. A second era is a second attack surface and not a
   relaxation of the first.
4. A server whose era is not known in advance can be connected with one
   call, and a server that speaks neither era fails with a message naming
   what it did say.

**Non-goals.**

- **A classic (dual-era) server.** AgentKit's own server stays modern-only.
  It already answers a legacy `initialize` with a diagnostic naming the
  versions it speaks, which is the failure mode a legacy *client* needs; the
  case this PRD fixes is the other direction. A dual-era server is a
  separate PRD, and §9 notes what this one leaves in place for it.
- **Prompts, completions, resource subscriptions, the Tasks extension.**
  Neither client has them today (README, *What is not built*). The classic
  client ships the same subset the modern one does: tools, resource listing
  and reading, and the notifications that keep the tool cache honest.
- **The authorization framework** (`2025-03-26` onward: OAuth discovery,
  dynamic client registration, token refresh against a remote server). A
  static bearer token through `headers` with `${VAR}` interpolation is what
  the modern client offers and what the classic one offers. Interactive
  OAuth is a product decision of its own, and it is orthogonal to the era.
- **Sending JSON-RPC batches.** `2025-03-26` permits them and `2025-06-18`
  removed them. The client never has a reason to send one. Receiving one is
  handled (§4.5) because a `2025-03-26` server may.
- **Roots and elicitation as features.** Both are server-initiated requests
  the client must *answer* under the classic era or the server hangs waiting.
  They are answered (§4.4), not implemented as capabilities: roots with what
  the embedder configured and nothing by default, elicitation with a refusal
  unless the embedder supplied a handler.

## 3. What carries over

Most of the client is not era-specific, and the shape of the existing code
already separates the two. Nothing in this table is rewritten:

| Piece | Where | Why it carries over |
|---|---|---|
| JSON-RPC envelope: `Message`, `ID`, `Error`, the strict `bindEnvelope`, `decodeFrame` | `mcp/jsonrpc.go`, `mcp/client.go` | JSON-RPC 2.0 is the same on both eras. The type-encoded correlation key and the case-sensitive closed member set are exactly the properties a second peer must not weaken. |
| The correlator | `mcp/jsonrpc.go` | Id generation and response correlation (REQ-GO-06) do not know what the ids are for. |
| stdio transport, pipe transport, process-group kill, reduced environment, stderr bounding | `mcp/transport.go`, `mcp/proc_*.go` | Classic stdio is newline-delimited JSON with no embedded newlines — the same framing `wire.NewNDJSON` already reads. REQ-MCP-CLIENT-10 applies unchanged. |
| The SSE decoder | `mcp/sse.go` | It already parses and discards `id:`; the classic transport needs it kept (§4.3). One field, not a second decoder. |
| Protocol structs: `ToolDefinition`, `Content`, `ToolsCallResult`, `ToolsListResult`, `Resource`, `ResourcesReadResult`, `SamplingParams`, `SamplingResult` | `mcp/protocol.go` | The modern structs are a superset of the classic ones on every type this client reads. A classic `tools/list` result carries no `resultType` and no `ttlMs`; the strict binder leaves an absent member zero, so the modern struct binds a classic result as it is. Verified by inspection of every member against the three classic schemas, and pinned by a test (§6). |
| `CapContent`, `QualifiedName`, `SplitQualified`, the argument pass-through in `Pool.adapt`, `schemaFrom` | `mcp/client.go`, `mcp/pool.go` | The cap, the naming convention and the float64 laundering rule are about the model's context and the tool registry, not the wire. |
| `ServerConfig`, `ConnectionOptions`, `ParseConfig`, `${VAR}` interpolation, `UnresolvedVariableError`, `resolveEnv`, `resolveHeaders` | `mcp/config.go`, `mcp/pool.go`, `mcp/transport.go` | One config vocabulary for both eras (§4.7). The credential rules (NFR-SEC-03, REQ-MCP-CLIENT-10) do not depend on the handshake. |
| Call limit, timeout, reconnect budget, the `is_error` surfacing (NFR-REL-03), audit (REQ-OBS-05) | `mcp/client.go` | Per-session policy over a connection. What "reconnect" means differs (§4.6); the budget does not. |
| The collision check at connect and its backstop in `Tools` (REQ-MCP-CLIENT-06) | `mcp/pool.go` | It reads a tool list; it does not care who produced it. |

What does **not** carry over, because the era defines it differently, is the
subject of §4: how a connection opens, what a request carries, what the
server may send unasked, what the remote transport looks like, and what a
reconnect has to re-establish.

## 4. Design

### 4.1 Shape: a second package, one pool

The classic client is a new package, `mcp/classic`, with its own connection
type. It imports `mcp` for everything in §3 and adds the era-specific
machinery; `mcp` does not import it. The pool learns to hold either.

Two alternatives were considered and are recorded so they are not re-asked.

*A dialect switch inside `ServerConnection`.* One type, an `era` field, and a
branch at every point the eras differ. There are eleven such points (§4.2 to
§4.6), several of them in the read loop and the reconnect path, which are the
two pieces of the client most sensitive to a wrong branch. The modern client
would acquire classic-only fields (a session id, a negotiated version, a
pending-server-request table) that are zero for the rest of its life, and
every modern test would be a test of a type that also does something else.
Ruling L-1's *"not a flag"* was written against exactly this shape. Rejected.

*A separate package with nothing shared.* Copies the correlator, the
envelope binder and the transports. The duplicate-key and case-sensitivity
properties would then hold in two places or in one, and the second copy is
the one that drifts. Rejected.

The chosen shape needs three things from `mcp`, none of which changes
modern behaviour:

- **A `Client` interface**, satisfied by `*mcp.ServerConnection` and by
  `*classic.Connection`, covering what `Pool` uses: `Name`, `Config`,
  `ListTools`, `CallRaw`, `RefreshTools`, `Alive`, `Dead`, `Close`. `Pool`
  holds `Client`s; `Pool.Add` accepts one; `Pool.Get` returns one. The
  concrete modern type is still what `Pool.Connect` returns, so no existing
  caller changes.
- **The shared plumbing made reachable.** The correlator, `decodeFrame`,
  `bindEnvelope` and the `link` (a transport, its correlator and its read
  loop's done channel) are unexported today. They move to
  `mcp/internal/rpc`, which both `mcp` and `mcp/classic` import. Nothing
  outside `mcp/` can reach it, which is the same visibility they have now.
  The SSE decoder moves with them and grows an `id` field.
- **A `Protocol` field on `ServerConfig`** (§4.7) and the `Client` type on
  the audit and collision paths. `Pool.Connect` ignores the field: it is the
  modern entry point and stays one.

The classic package's entry point mirrors the pool's:

```go
// Connect opens cfg according to cfg.Protocol: "classic" performs the
// handshake, "2026-07-28" delegates to pool.Connect, and "auto" (the
// default when the field is empty) probes (§4.8). The connection is
// discovered, checked for shadowed names, armed for reconnection and added
// to the pool, exactly as pool.Connect does for a modern server.
func Connect(ctx context.Context, pool *mcp.Pool, cfg mcp.ServerConfig,
    env []string, secrets func(string) string) (mcp.Client, error)
```

An embedder that imports `mcp/classic` and calls `classic.Connect` gets both
eras through one call. One that does not keeps `pool.Connect` and is
modern-only, as today. Nothing is registered by import side effect, which is
the rule the README states for providers and the one this follows.

### 4.2 Opening a connection: the handshake

A classic connection is not usable until `initialize` has been answered and
`notifications/initialized` sent. The sequence, with the rules the client
enforces:

1. Send `initialize` with `protocolVersion: "2025-06-18"`, `clientInfo`, and
   `capabilities` built by the same rule as the modern `requestMeta`:
   `sampling` only when `AllowSampling` is set and a handler exists;
   `roots` only when the embedder configured roots (§4.4); `elicitation`
   only when a handler exists. Advertising a capability the client will
   refuse invites a server to build a flow around it, and here the failure
   lands as a hung request rather than a wasted MRTR round.
2. The response's `protocolVersion` is the negotiated version. If it is one
   of `2025-06-18`, `2025-03-26`, `2024-11-05`, the connection remembers it;
   otherwise the client closes the transport and fails with an error naming
   both versions. That is what the classic spec requires of a client whose
   offer is not met, and it is the diagnostic a user needs.
3. Send `notifications/initialized`. Only now may any other request go out,
   and the client enforces the order: a `tools/list` issued before step 3 is
   an `ErrNotInitialized`, not a request. Servers reject or ignore early
   requests, and the failure is a timeout that names nothing.
4. `serverInfo`, `capabilities` and `instructions` are stored; `Info()`
   returns them in the same `DiscoverResult` shape the modern connection
   returns, with `SupportedVersions` holding the one negotiated version, so
   a caller that reads `Info()` does not branch on the era.

`initialize` runs under `timeout_s` like every other request. With a
handshake in the client again, **NFR-PERF-02 is restored from design
guidance to a budget**: a benchmark of the in-process handshake and a
threshold test that fails the build, which is what its demotion note asked
for. The 2-second figure it names is for a subprocess spawn plus handshake
against a typical local server; the in-process benchmark pins the client's
own share of that and is given a threshold of 1 ms, the same order as
NFR-PERF-01.

### 4.3 What a request carries, and what a result does not

Nothing is injected into `_meta`. The classic `_meta` is the open namespace
`2025-06-18` defines with one reserved member, `progressToken`, which this
client does not use. The modern `withMeta` is not called; the classic
request builder marshals the params as they are.

Results carry no `resultType`; the client treats every result as complete,
because that is what the spec says and because there is nothing else it
could be. Results carry no `ttlMs`; the tool cache is valid until
`notifications/tools/list_changed` arrives or `RefreshTools` is called
(REQ-CACHE-07's original text, which is the classic rule). A server that
does not advertise `tools.listChanged` will never send the notification, and
the cache is then valid for the life of the connection: that is the era's
contract, and inventing a TTL the server did not send would re-list on every
turn against a server that promised nothing changed.

Over HTTP, every request after the handshake carries two headers the
modern transport does not: `Mcp-Session-Id`, echoing the value the server
returned on the `initialize` response if it returned one, and
`MCP-Protocol-Version`, the negotiated version, sent only when that version
is `2025-06-18` (earlier revisions do not define the header, and a strict
`2025-03-26` server may reject an unknown one). The modern routing headers
`Mcp-Method` and `Mcp-Name` are **not** sent: they are `2026-07-28`'s, and a
classic server that validated headers against the body would find nothing
to validate them with.

The session id is server-issued and opaque. The client validates it before
it ever echoes it — visible ASCII, `0x21` to `0x7E`, the range the spec
reserves — and refuses a connection whose server issued anything else. A
value outside that range is not a session id; it is an attempt to put a
control byte in a header the client will send on every request.

### 4.4 What the server may send unasked

Under the classic era the server may send the client requests and
notifications at any time, on any stream. The modern read loop warns and
drops a server request; the classic one must answer every one of them,
because a classic server that asked and was not answered waits forever, and
the tool call that triggered the question hangs with it.

| Server sends | Client does |
|---|---|
| `ping` (request) | Answers with an empty result, always, before any other work. A server that pings to detect a dead client and gets no answer disconnects. |
| `sampling/createMessage` (request) | REQ-MCP-CLIENT-08's gate and audit, unchanged: refused unless `allow_sampling` is set and a handler exists, and every request audited whether allowed or refused. **A refusal is a JSON-RPC error response, never silence.** The modern client refuses by failing the tool call; the classic one must tell the server, or the server's tool call never completes and ours times out with a message about the wrong thing. |
| `roots/list` (request) | Answers with `ConnectionOptions.Roots` if the embedder set it, otherwise with an empty list. Never the workspace, never the working directory: a root is a grant of filesystem scope to a server, and REQ-SEC-08's posture is that grants are explicit. The capability is advertised only when roots are configured (§4.2). |
| `elicitation/create` (request) | Answered by `ConnectionOptions.Elicit` if set, otherwise refused with a JSON-RPC error whose message names the method and says this client does not implement it, and audited like a refused sampling request. |
| Any other request | Refused with `MethodNotFound`. Named, so the server's author sees which method the client lacks. |
| `notifications/tools/list_changed` | Invalidates the tool cache, exactly as the modern client does on its subscription stream. |
| `notifications/resources/list_changed`, `notifications/resources/updated` | Delivered to `ConnectionOptions.OnNotification` if set; otherwise dropped. No resource cache exists to invalidate. |
| `notifications/message` (logging) | Forwarded to `Warnf` with the server's level and logger name, bounded by the wire limits the frame already passed. The `logging` capability is never *requested* (no `logging/setLevel`), so a server sends what it sends. |
| `notifications/progress` | Dropped. Nothing in this client exposes progress, and the modern client has no equivalent to keep in step with. |
| `notifications/cancelled` | Dropped. It cancels a request the *server* is answering for us, and the client has no server-side handlers to cancel. |

Server requests are dispatched on their own goroutine per request, bounded
by the same handler cap the server uses for its own inbound requests. The
read loop must not run them inline: a sampling handler that calls a model
takes seconds, and every response frame behind it would wait.

### 4.5 Batches on the way in

A `2025-03-26` server may answer with a JSON-RPC batch, a top-level array of
messages. The strict envelope binder rejects a top-level array today (*"a
JSON-RPC frame is an object"*), and that stays the rule for the modern
client. The classic read loop accepts an array **only when the negotiated
version is `2025-03-26`**, splits it into its members, and runs each through
the same strict binder. The array is bounded by `MaxContainerLen` and
`MaxNodes` before it is split, like everything else that arrives. A batch
under `2025-06-18` or `2024-11-05` is a malformed frame and poisons the
connection (REQ-SEC-11.4): neither revision permits one, and a peer sending
what the negotiated version forbids is a peer whose framing cannot be
trusted.

### 4.6 Transports

**stdio** is `mcp.StartStdio` unchanged, with the handshake on top. The
subscription keeper the modern pool starts (`keepToolsSubscribed`) has no
classic equivalent and is not started: under the classic era
`tools/list_changed` arrives unsolicited on the one stream there is.

**Streamable HTTP (`2025-03-26` / `2025-06-18`)** is a new transport,
`classic.StreamableHTTP`, built on `mcp/internal/rpc`'s HTTP plumbing (the
endpoint parsing, the redirect refusal, the header interpolation, the
bounded body read, the SSE pump). What it adds:

- The `initialize` POST is sent with no session id; the response's
  `Mcp-Session-Id` header, if present, is validated (§4.3) and attached to
  every later request.
- A POST that is a request is answered with JSON or an SSE stream scoped to
  that request, as today. A POST that is a notification or a response to a
  server request gets `202` and nothing to read, as today.
- **A GET stream is opened after the handshake** when the server advertised
  `tools.listChanged`, or when sampling is allowed, or when roots or an
  elicitation handler are configured — that is, whenever there is something
  the server might need to send that no POST would carry. A `405` means the
  server offers no stream, and the client records that and does not retry;
  a `404` is a session the server has expired (below). The stream is not
  opened for a server that advertised nothing and was granted nothing: it
  would hold a request open against a remote for the life of the session to
  deliver nothing, which is the reason the modern pool does not subscribe
  over HTTP either.
- **`Last-Event-ID` resumption on the GET stream.** The SSE decoder keeps
  the last `id:` it saw; when the stream ends without the transport closing,
  it is reopened with that header, bounded by the reconnect budget. A stream
  that ends *with* no ids ever seen is reopened without the header.
- **A broken POST stream is not re-issued.** The modern client re-issues a
  request whose response stream broke, once, with a new id, because
  `2026-07-28` has no other recovery. The classic era has one: the client
  reopens the GET stream with `Last-Event-ID` and the server MAY replay what
  it would have sent. The classic client does that and only that. It never
  re-POSTs a `tools/call`, because the server may have executed it and a
  tool that ran twice is the failure NFR-REL-03's `is_error` exists to
  prevent. If the server does not replay (no `id:` on the broken stream, or
  a `405` on the GET), the call fails as `is_error` naming the reason.
- **`404` on any request after the handshake means the session expired.**
  The client drops the session id, re-runs the handshake on the same
  endpoint, and re-issues the request that hit the `404` only if it was a
  list or a read — never a `tools/call`, for the reason above. Each
  re-handshake spends one unit of the reconnect budget.
- **`DELETE` on `Close`**, with the session id, when the server issued one.
  A `405` in reply is fine: the spec lets a server refuse client-initiated
  termination. Any other failure is logged and ignored; the transport is
  going away regardless.

**HTTP+SSE (`2024-11-05`)** is the two-endpoint transport: a GET on the
configured URL opens an SSE stream whose first event, `endpoint`, names the
URL to POST to; every server-to-client message arrives on that stream, and
every POST is answered `202`. It is deprecated upstream and still what a
large share of remote servers deployed before mid-2025 speak. It is a third
transport type, `classic.SSE`, and whether it ships in the first cut is
decision 3 (§8). If it ships, one rule is non-negotiable: **the `endpoint`
URL must have the same origin as the configured URL**, scheme, host and port,
or the connection is refused. The configured headers carry the server's
bearer token and are sent on every POST; a server whose `endpoint` event
pointed at another host would receive our credential there. This is the
redirect rule (`TestTheDefaultHTTPClientDoesNotFollowRedirects`) in a
different coat, and it is the reason the transport is not a small addition.

The `transport` config key, which today rejects everything but
`streamable-http` with an error saying the build is modern-only, becomes
meaningful again: `streamable-http` (the default for a `url` server) and,
if decision 3 is yes, `sse`. An unknown value is still an error.

### 4.7 Configuration

One new key on `[[mcp.servers]]`:

```toml
[[mcp.servers]]
name     = "github"
command  = "npx"
args     = ["-y", "@modelcontextprotocol/server-github"]
protocol = "auto"        # "auto" | "classic" | "2026-07-28"; default "auto"
```

`ParseConfig` reads it into `ServerConfig.Protocol`. An empty value is
`auto`. `Pool.Connect` stays modern-only and does not act on the field, so
an embedder that never imports the classic package sees no behaviour change
from a config that leaves it empty. It does not ignore the field silently,
though: handed `classic`, `Pool.Connect` refuses with an error — *"server %q
asks for the classic protocol; pool.Connect is modern-only, use
classic.Connect"* — and handed `auto` it proceeds modern-only and warns
once that `auto` is honoured by `classic.Connect` alone. `ParseConfig`
cannot know which entry point the host will call, so the diagnostic lives
where the choice is made. A misconfiguration should name its fix.

Everything else on the entry is shared: `env`, `headers`, `tool_prefix`,
`allow_sampling`, `per_session_call_limit`, `per_session_reconnect_limit`,
`timeout_s`. Two keys are classic-only and ignored with a warning by the
modern path:

- `roots = ["file:///path/one", "file:///path/two"]` — what `roots/list` is
  answered with (§4.4). Absent means an empty list.
- `ping_interval_s = 0` — client-initiated keepalive pings, default off. A
  server does not need them to function; an operator behind a proxy that
  drops idle connections may want them.

### 4.8 `auto`: finding out which era a server speaks

There is no version-agnostic probe. A modern server has no `initialize`; a
classic server has no `server/discover`. What each one does with the other's
opener is, however, well defined and cheap:

- A classic server answers `server/discover` with `MethodNotFound`
  (`-32601`). Every classic revision requires that for an unknown method.
- A modern server answers `initialize` with `UnsupportedProtocolVersion`
  (`-32022`) whose `data.supported` lists what it speaks — the spec makes
  this a SHOULD and AgentKit's own server does it — or, from a server that
  did not follow the SHOULD, with `MethodNotFound`.

`auto` sends **`initialize` first**, because that is the era most servers
speak and the probe that succeeds on the first round trip most often. The
outcomes:

| `initialize` answered with | Then |
|---|---|
| A result with a `protocolVersion` the client supports | Classic. Continue at §4.2 step 3. |
| A result with a version it does not support | Fail, naming both versions. The server *is* classic but too old or too new for this client, and trying modern next would only add a second confusing error. |
| `-32022` with `data.supported` containing `2026-07-28` | Modern. Over stdio, `server/discover` goes out on the same transport. Over HTTP the classic transport is closed and `pool.Connect` opens a modern one: the two transports differ in what they send, and reusing one across eras is how a session id or a routing header ends up on the wrong wire. |
| `-32022` naming versions the client speaks under neither era, or `-32601` | Modern, tentatively: send `server/discover`. If that also fails, the connection fails with **both** answers in the message: what the server said to `initialize` and what it said to `server/discover`. A server that refuses both openers has told us what it is not, twice, and the user should see both. |
| Anything else (a transport error, a malformed frame, a timeout) | Fail as the modern client would. Auto-detection does not retry an error that is not about the era. |

The probe costs one extra round trip against a modern server and none
against a classic one. An embedder that knows what it is connecting to
writes `protocol` explicitly and pays nothing.

Auto-detection happens **once, at connect.** A reconnect re-opens the era
that was detected; a server that changed era between two spawns is a
different server, and the reconnect fails with the mismatch named rather
than silently re-probing on the session's reconnect budget.

### 4.9 What the model sees

Nothing new. A classic tool is adapted by the same `Pool.adapt`, carries the
same qualified name, the same `MCPServer`, the same converted schema, the
same `Execute` closure that passes the model's argument bytes through
verbatim, and returns the same `ToolResult` shapes. The result cap is the
same cap. The audit event is the same event. `BeforeToolCall`, the
allowlist, plugin hooks and `OnToolUse` see the qualified name, as
`TestMCPToolsAreGatedByQualifiedNameEverywhere` requires, and that test is
run a second time over a classic connection to prove it.

## 5. The import graph after the change

```
mcp/internal/rpc  ──► wire
mcp               ──► core, schema, wire, internal/toml, internal/diag, mcp/internal/rpc
mcp/classic       ──► mcp, mcp/internal/rpc, core, wire
agentkit (root)   ──► (unchanged; does not import mcp)
examples/mcp      ──► agentkit, mcp, mcp/classic, …
```

No cycles, no new module, no new dependency. `mcp/internal/rpc` is
importable only from under `mcp/`, which is the visibility the moved code
has today. The root never imported `mcp` and still does not; the classic
package sits beside the modern one, below nothing that matters to the loop.

## 6. Tests

The modern client's tests do not change, and that is the first assertion:
`go test ./mcp/...` is green before and after step 1 of §7 with no test
edited. Then, per the repository's practice, each classic behaviour gets a
test that was watched to fail against the wrong implementation. The
mutations that matter, and the tests that must catch them:

| Mutation | Test that catches it |
|---|---|
| Send `tools/list` before `initialize` has been answered | `TestNoRequestLeavesBeforeTheHandshakeCompletes` |
| Skip `notifications/initialized` | `TestInitializedIsSentAfterTheHandshakeAndBeforeAnyRequest` |

## 8. Decisions for the reviewer

1. **Package layout: `mcp/classic` over `mcp/internal/rpc`** (§4.1), or the
   classic connection as a second type inside `mcp` with the plumbing left
   where it is. Recommendation: the separate package. It is what L-1 asked
   for, it keeps the modern client's file set and test set untouched, and it
   makes "which era am I reading" a package name rather than a field.
2. **`auto` as the default for `classic.Connect`** (§4.7), or `classic` as
   the default and `auto` opt-in. Recommendation: `auto`. The embedder that
   reached for this package wants a server to work; the one round trip it
   costs against a modern server is the cheapest way to make the common
   config correct without a field.
3. **HTTP+SSE (`2024-11-05`) in the first cut** (§4.6), or deferred to a
   follow-up with the same-origin rule recorded now. Recommendation: defer,
   and record the rule. Every server generated by an SDK since mid-2025
   speaks Streamable HTTP; the deprecated transport is a real but shrinking
   set, and the same-origin hazard is the part worth getting right rather
   than fast. If a reviewer knows of a server this PRD must reach that
   speaks only HTTP+SSE, the answer flips.
4. **Never re-POST a `tools/call` on a broken classic stream** (§4.6), or
   re-issue once as the modern client does. Recommendation: never. The
   modern client re-issues because it has no other recovery; the classic
   era has resumption, and a tool run twice is worse than a tool call that
   reports it does not know whether it ran.
5. **Restore NFR-PERF-02 as a budget** (§4.2) with the in-process
   threshold, or leave it demoted and add only the benchmark.
   Recommendation: restore. Its demotion note says exactly when to.
6. **The PRD amendment is a new version, 0.5.0** (§10), or the existing
   0.4.0 text is edited in place. Recommendation: 0.5.0, non-breaking,
   amending REQ-MCP-CLIENT-02, -03, -08, NFR-COMPAT-02 and NFR-PERF-02 with
   the same "amended in" convention every earlier version used. The 0.4.0
   decision stays in the changelog as what it was.

## 9. Noticed, not part of this change

- **A dual-era server** would let the classic client be tested against the
  shipped server the way the modern one is, and would let Claude Desktop
  and other classic hosts connect to an AgentKit server. The test server in
  §6 is a start and not the thing: a real one needs the session table, the
  handshake state machine in `Serve`, and the GET stream on the HTTP
  handler. Its own PRD.
- `ConnectionOptions.Sampling` is typed for the classic shape already
  (`SamplingParams` → `SamplingResult`); the modern client wraps it in an
  MRTR answer. One handler serves both eras, which is why §4.4 adds no new
  sampling option.
- `mcp.ServerConnection.Info()` returns a `DiscoverResult` whose
  `SupportedVersions` is the server's whole set; the classic connection
  returns the one negotiated version in the same field (§4.2). A caller
  that wants to know which era it is talking to reads `Client.Config().
  Protocol` after connect, which `classic.Connect` fills in with the
  detected value. Worth a line in the package doc.
- The `mcp` example's `--external` flag documents *"takes any 2026-07-28
  server"* and names `@modelcontextprotocol/server-github` as the thing to
  try, which is a classic server and cannot have worked. §10 fixes the doc;
  after step 6 the flag goes through `classic.Connect` and the example
  works as written.
